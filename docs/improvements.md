# 审计发现与优化路线

> 状态：**待实施提案（to-do）**。基于 2026-10-30 对 `master` 分支的静态代码审阅，未在本次文档工作中修改业务代码，也**没有**声称已执行 `go test`、race 检测或 NAS 压力测试。系统现状及示例参见 [architecture.md](architecture.md)。

## 原则与目标

目标是提高大规模 NAS 场景下的**正确性、安全性、资源可控性和可维护性**，而不是追求组件数量。

保留以下方向：

- 单 Go binary、SQLite 索引与任务状态、无 Redis/消息队列/独立搜索服务；
- 只读访问源媒体，扫描与元数据增强分离；
- 小型 `Enricher{Match, Enrich}` 接口、一个共享 `Meta`、顺序增强 + 多文件并发；
- 懒加载封面/字幕、按需 HLS、浏览器优先直接播放；
- 无构建 Preact + htm 前端；按需缓存本地静态资源。

约束：本篇记录**问题和拟采取的改进**，不是当前已支持的功能，也不是强制要求大重构。先为确认的缺陷补回归测试，再进行必要的最小修改。

## 第一阶段：索引正确性、用户数据和访问边界

### R1. 防止旧 Worker 的结果覆盖新状态

**现状**：`Pipeline.feed` 获取 `store.File` 快照后交给 Worker。扫描器发现同路径变化时把 `meta_ver=0`，而 `SaveResults` 无条件按 `WHERE id=?` 更新 `kind/title/meta/meta_ver`。因此“旧文件处理完毕 -> 覆盖新文件待处理状态”的竞态成立。

**建议**：

1. 在 `files` 增加只在文件来源或与增强结果相关的输入变化时递增的 `revision`（或等价 generation）。
2. Worker 获取 `id + revision`，写回时执行条件更新，例如 `UPDATE ... WHERE id=? AND revision=?`。
3. 检查 `RowsAffected`：零行意味着任务结果已过期，必须丢弃，保持/重新建立新版本的待处理状态；不能把零行视为正常完成。
4. 手动匹配、刷新和扫描对同一对象的修改应使用同样的修订/事务语义；不能让后台结果覆盖用户刚刚锁定的匹配。
5. 保证“被删除并同路径重建的文件”不会继承不该继承的旧结果（ID 不可错误复用；必要时还要校验来源版本）。

**验收**：用受控阻塞增强器在 `Enrich` 中间改写并重扫文件；旧结果写回必须失败，新文件最终重新增强。并发 `Rematch` / 手动锁定与后台保存不得丢失用户选择。

### R2. 扫描错误不得变成隐式删除

**现状**：`Scanner.sync` 枚举 `os.ReadDir` 后，对 `entry.Info()` 错误直接 `continue`。后续“没进入 current”的名字归类为 removed，执行整条记录及子树删除。

**建议**：

- 区分**明确不存在**与**无法读取**。某个条目 `Info` 失败时，本次该目录协调应报错并保留旧索引，不得基于不完整快照删除。
- 确保先获得可验证的完整目录视图，再开启该目录更新事务；事务失败时整体回滚。
- 对扫描期间目录频繁增删的情况采用安全重试/下次扫描，而不是为了保持扫描成功而跳过未知项。
- 可记录扫描错误和该 Root 的状态，但不要吞掉会影响删除决策的读取错误。

**验收**：模拟 `entry.Info()` 失败、`ReadDir` 失败、目录在扫描期间变化；旧条目（含子树与用户数据）保持不变，后续成功扫描才正确协调变更。

### R3. 将不可重建的用户覆盖信息持久化

**现状**：`schemaVersion` 不一致时 `store.reset` 删除并重建包括 `files` 在内的表；用户手动设置的 `meta.locked` 和 `meta.tmdb` 也存在 `files.meta`。这些不是可从源媒体恢复的纯派生数据。

**建议**：

- 逻辑上分为：`source`（文件信息）、`derived`（自动增强结果）、`overrides`（人工确认或覆盖）。
- 在同一个 SQLite 数据库中增加小型持久化 `overrides` 表，例如按稳定的 `(root, path)` 标识资源，并明确路径重命名、Root 删除、文件被替换时的保留策略。
- 将 schema 升级改为可审计的迁移；**绝不在未备份/未迁移用户数据时静默丢弃 overrides**。
- 读取展示时先取自动识别结果，再按规则应用用户覆盖；自动重新增强不能清除用户选择。
- 若未来支持标题、海报、语言等手动修订，沿用同一覆盖模型，不逐一塞进不透明的自动 `meta` 字段。

**验收**：锁定 TMDB、重启、升级 schema、重新扫描、重新增强后锁定保持；明确测试改名、移动、删除、重新出现及解除锁定的行为。

### R4. 文件真正打开时仍需限制 Root 边界

**现状**：扫描时跳过符号链接，但 `Abs` 基于索引路径构造绝对路径；`raw`/元数据解析/缩略图/HLS 等调用会再次打开这个路径。如果已索引文件在此期间被攻击者或可写存储替换为指向 Root 外部的 symlink，普通 `os.Open` 会跟随它。风险依赖第三方是否能修改目录及服务进程的文件权限。

**建议**：

- 把“可信 Root 内安全打开”集中成统一能力，所有源文件读取方共用，不仅对 `/raw` 做防护。
- 避免仅做 `filepath.Clean`、`EvalSymlinks` 后再 `os.Open` 的检查/使用时间差（TOCTOU）。优先考虑安全的基于目录句柄的受限打开；兼容当前 `go 1.22.4` 的实现与升级 Go 后可用的 API 分开评估。
- 统一禁止或明确规定 symlink 使用策略；确保 Root 本身、路径的中间层和目标都满足策略。
- 保留部署层的最小 OS 权限、只读挂载和独立数据目录，避免单一代码检查成为唯一安全边界。

**验收**：在索引后把文件或其父目录替换成 Root 外 symlink；`/raw`、封面、字幕、探测与播放均不得访问外部目标。增加并发替换场景及不同平台测试。

## 第二阶段：增强依赖、扫描与任务重试

### R5. 明确父子与旁路文件的依赖失效

**现状**：`Folders` 根据下层视频数、已有视频元数据、NFO、海报做识别；`Videos` 又可能引用父 Show 的 TMDB 结果。父目录、子文件和 sidecar 是不同任务，完成顺序不固定。子文件后来增强成功时，父目录不一定再次失效；手动更改父 Show 匹配后，单集也未必会立刻重算。

**建议**：

1. 先列出**确实影响识别**的依赖：`movie.nfo`、`tvshow.nfo`、电影主视频时长、海报/背景、Show TMDB、Season/Episode 结构。
2. 当文件插入/删除/更新及关键增强结果发生变化时，仅使受影响的父/子对象待处理；采用增量失效，不做全 Root 重算。
3. 失效应幂等、可去重，避免子项刷新父项再无限触发子项。
4. 对元数据解析后的父子读取使用一致快照或版本机制（与 R1 结合）。
5. 不必引入通用 DAG 引擎；轻量显式依赖规则即可。

**验收**：先增强文件夹、后增强视频；后来放入 `movie.nfo`/`poster.jpg`；删除主视频；修改 Show 手动 TMDB；新增或删除单集。相关页面最终一致，且无无界重复任务。

### R6. Root 离线、卸载和切换挂载

**现状**：缺失 Root 会标为 offline；对“以前非空、现在为空”的 Root，主要依设备号判断是否卸载。不同挂载方案下可能不能可靠判断新目录是否其实属于错误的文件系统。

**建议**：

- 引入可靠可观察的 Root 状态和扫描策略：`online` / `offline` / `mount changed` / `error`。
- 配置可选挂载校验（设备、挂载标识、指定 marker 文件等），尤其适用于 NAS 外接盘、NFS/SMB 和 bind mount。
- 根目录读取不可信、挂载改变、局部读取失败时倾向保留已有索引；清空需要明确的可验证条件或用户确认。
- 手动 `force=1` 的语义要写入 API 文档，并提醒它是具有删除索引风险的确认操作。

**验收**：拔盘、同设备空目录、不同设备空挂载、挂载为错误非空目录、网络断连/恢复、人工强制扫描，均有可预期且可恢复的行为。

### R7. 文件变化检测精度与实时性

**现状**：Scanner 记录 `UnixMilli()`，对于同尺寸同毫秒的修改可能视为未变；浏览时 `Stale` 看目录 mtime，文件内容被原地覆盖不一定会修改目录 mtime。周期全盘扫描也按文件大小与毫秒 mtime 比较。

**建议**：

- 改用更高精度的文件 mtime（或 OS 提供的 change token），兼顾网络文件系统的时间精度与时钟语义。
- 不把目录 mtime 当成所有内容变化的充分证据；保留周期协调。
- 对特定目录提供明确的“强制 stat 子项”能力；文件内容哈希可作为可选的昂贵手段，**不建议默认对全部 NAS 文件做哈希**。

**验收**：原地覆盖同大小文件、极短时间内重复修改、不同时间戳精度的挂载，能触发适当重新增强。

### R8. 临时错误使用逐任务退避，不应全局停工

**现状**：任意一个 `ErrTransient` 会令整条 Pipeline 的 `paused` 时间设置为当前时间加五分钟；与该错误无关的本地文件也暂停处理。

**建议**：把失败次数和 `retry_after` 绑定到文件/任务，指数退避并设上限；网络服务失败时可单独增加针对服务端点的简单限速/熔断，本地 Probe、Photo 等任务继续执行。避免数据库错误时不断热循环。保留可观测的错误统计和显式重试入口。

**验收**：TMDB 超时期间，本地音乐和图片依然继续增强；失败任务延后而不丢失，重启后仍可恢复。

### R9. 缩略图任务的 CPU/内存上限和负缓存

**现状**：`Thumbs` 用 `runtime.NumCPU()` 作为并发上限；解码大图片有明显的内存压力。非网络类生成失败通常写入零字节文件，形成长期负缓存。

**建议**：对图片解码、FFmpeg 取帧和 PDF 预览分别设较小并发预算；限制像素总数与来源文件大小，避免解码爆内存。对临时失败采用 TTL 负缓存/允许重试；真正不受支持的类型才可以较长时间缓存失败。注意 `writeFile` 并发对同名 tmp 的安全性。

**验收**：多张超大图同时请求时内存有界；网络短暂故障恢复后封面能够重试；相同 key 的并发请求只执行一次生成。

### R10. 字幕转换须有明确内存上界

**现状**：外挂字幕通过 `os.ReadFile` 整体读取以检测编码；FFmpeg 输出使用无明确上限的 `bytes.Buffer`。多个请求还可能并发重复转换同一字幕。

**建议**：编码检测只读取有界前缀；对源文件大小、标准输出和标准错误设上限，必要时直接流向临时文件并原子发布；同字幕 key 合并正在运行的任务；对失败与取消设置合理清理。

**验收**：超大字幕/异常 FFmpeg 输出不造成进程 OOM；并发同一字幕只转换一次，客户端取消不会破坏缓存。

## 第三阶段：播放、搜索与展示性能

### R11. HLS 首次探测和缓存

**现状**：`pkg/hls` 在 `Open` 建立完整 VOD 时间轴，不提前编码。复制视频时 `timeline` 通过 ffprobe 遍历 packet header，按关键帧切片；片段按需生成，多个会话共享正在运行的工作和缓存。当前时间轴/片段缓存主要归属于 Manager 生命周期，重启不保证复用。

**建议**：

- 测量本地 SSD、机械盘、NFS/SMB、不同长度/码率文件的首次开始时间、time-to-first-frame、seek 延迟和读取量。
- 优先按 `source path + size + high-resolution mtime + rendition args + tool/format version` 缓存时间轴；明确源变化失效和损坏重建。
- 再评估片段是否值得跨进程持久化，防止中断残留、磁盘配额失控及旧缓存错用。
- 保持现有共享工作、并发限制、直接播放优先、独立 HLS 包的职责边界；不要轻易为了优化而全片预转码。

**验收**：重播同文件时不重复昂贵的关键帧探测；源文件修改后旧时间轴不得复用；seek/字幕与播放时长正确，缓存始终遵守配额。

### R12. 搜索、前端资产和元数据显示

- **搜索**：FTS5 trigram 用于名称与标题；中文等短于三字符的查询退回 `LIKE`。先测量百万级条目及常见中文查询，再决定是否增加额外搜索策略/索引；不要预先引入 Elasticsearch。
- **前端资源**：目前 Preact/htm 入口与 hls.js 从 CDN 动态加载。可将固定版本 ESM 文件随 `embed.FS` 内置，保持零构建、单 binary，提升 NAS 离线运行稳定性；同时检查 CSP 和缓存版本策略。
- **显示信息**：当前 `title()`、`subtitle()` 和 `Details` 负责展示，`Meta.Info` 存结构化键值。若继续增强 `line1/line2/line3`，建议保留源数据结构，仅在 UI 或统一 ViewModel 派生，不增加重复且难同步的数据库显示字段。
- **扩展器**：`Music` 专辑/艺术家聚合、图书系列聚合可循序扩展；除非真实需要，不引入动态 Go plugin 或复杂依赖容器。

## 推荐实施批次

| 批次 | 先做什么 | 交付与验收 |
| --- | --- | --- |
| 1：正确性和安全 | R1、R2、R3、R4 | 相关回归测试；过期写回被拒绝、扫描失败不误删、手动选择不丢、源路径不逃逸 Root |
| 2：关系和任务状态 | R5、R6、R7、R8 | 父子失效规则、Root 状态、文件变更精度、逐任务重试；并发/离线测试 |
| 3：资源与播放 | R9、R10、R11 | CPU/内存/磁盘配额、字幕边界、HLS 时间轴优化；压力测试 |
| 4：体验与伸缩 | R12 | 大库搜索与渲染指标、离线前端资源、需要时增加媒体聚合 |

每批都应坚持：

1. 最小变更、明确职责，尽量不引入新基础设施。
2. **先可复现的测试，后修复**；有竞争条件时配合 `go test -race ./...`（并说明它只能检测实际执行路径）。
3. 核心路径验证：`go test ./...`；scanner 的失败/删改、用户锁定/重启、无网络增强、HLS seek、字幕与多个同时播放会话。
4. 通过有代表性的 NAS 数据集（建议 10 万/100 万索引项）测量：扫描耗时、SQL 查询延迟、待处理吞吐、峰值 RSS、缩略图并发与首帧时间；**指标应实测而不是在文档中预设“已达到”**。
5. 每次变更同步更新这两份文档中的“现状”与“待实施”状态，避免设计文档与代码长期漂移。
